Release 1.3.1 – 1.3.6 · 03 Sep 2026

Core Facility Tracker — what’s new

Six releases in one day, all pointed at the same seam opened up by 1.3.0’s billing work: a booking is only as good as the Group/Lab it’s filed under. Assigning people or core staff now waits for one; the lab’s standing discount follows automatically and can be revoked per-booking or for good; and a handful of smaller fixes — safer sample-data reseeding, a real favicon, a lockable single-instrument booking, a full screenshot gallery — round out the batch.

In detail

The three changes worth a screenshot.

Assign People and Assign Core Staff both wait for a Group/Lab new

Both pickers now lock the same way: with no Group/Lab chosen yet, clicking either dropdown shows a not-allowed cursor and a “Choose Group/Lab First” hint instead of opening the list. It makes sense once you notice every person and every core-staff member on record already belongs to a lab or group — the picker has nothing meaningful to filter until it knows which one.

  • People got the lock in 1.3.4; Core Staff got the identical lock two releases later, in 1.3.6.
  • Already-assigned people or staff are never removed by this — only adding more is blocked.
  • Picking a Group/Lab — directly, or auto-filled from the project’s PI — unlocks both immediately.

The lab’s standing discount, applied automatically — and revocable new

Choosing a Group/Lab for a booking offers that lab’s standing discount right away, live in the cost breakdown. In Admin Mode, a Revoke/Apply control on that line lets you turn it off — and asks whether that’s just for this booking or for every future booking under that lab (the latter edits the lab’s standing rate in Settings, same as changing it there directly). Re-applying restores the rate with no further prompt.

  • Picking a project auto-fills the Group from its PI’s lab; it can also be set directly for a facility-wide booking.
  • A booking now stores which Group/Lab it was made under, so reopening it restores the exact filter and discount state rather than re-deriving it live.

And it rolls straight into the project’s running total

Project Costs — the per-project list of booking subtotals, pre-tax figures, and totals, with a running total for the project — already existed as of 1.3.0. It didn’t need a code change to pick up 1.3.1’s discount work: each booking’s total is computed and snapshotted at save time, discount included, so the running total downstream was always going to reflect whatever discount that booking actually got.
