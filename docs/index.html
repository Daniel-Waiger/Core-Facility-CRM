Release 1.3.7 – 1.3.9 · 04 Sep 2026

Core Facility Tracker — what’s new

Three releases about trust rather than new features. 1.3.7 moved the whole app off a stock template palette onto one of its own, recoloured in both themes with contrast checked. 1.3.8 came out of an architecture and feature review of the codebase and fixes what that review found: four trash icons that deleted your data on a single click now ask first, a dialog that misdescribed what deleting a project does now tells the truth, deletes no longer leave dangling references behind, and a discount line that could overstate itself now adds up. Then documenting 1.3.8 turned up one more — a pair of controls that had been invisible all along.

In detail

The four changes worth a screenshot.

Four one-click deletes now ask first new

A review of the codebase turned up an inconsistency nobody would have enjoyed discovering the hard way: while deleting a project, a person, or an instrument had always asked for confirmation, four trash icons deleted immediately on a single click. A stray tap on a phone or a mis-click in a long list took the record with it, and there is no undo in a local-first app.

  • Bookings (in a project’s Meetings & Syncs card), milestones, custom metadata fields, and file attachments now each confirm first, naming the record about to go.
  • A booking’s confirmation also warns that its billing line items — assigned instruments and core staff — are deleted along with it.
  • The booking edit dialog’s own Delete button keeps its single confirmation; the two paths share one deletion routine, so nothing double-prompts.

Delete Project stops claiming it will delete your bookings fixed

The old dialog offered to delete the project “and all its milestones, files, and meeting records”. The first two were true. The third never was: the database unlinks a deleted project’s bookings rather than removing them, so they survive as facility-wide bookings — which is the right behaviour for billing history, and the opposite of what the dialog promised. Anyone who read it carefully would have been reluctant to delete a finished project at all.

  • The dialog now states plainly what is deleted (milestones, files, custom fields) and what is kept (the bookings, as facility-wide).
  • The delete itself now clears the project’s linked records explicitly instead of trusting the database to cascade — see the note below.

Deleting a person or an instrument says what happens to the billing new

Removing someone who has been on bookings raises a fair question: what happens to what was already billed? The answer is that saved totals stay exactly as they were — a booking’s cost is snapshotted when you save it, so it remains a record of what was charged rather than a live recalculation that quietly changes when the roster does. The dialogs now say that instead of leaving you to guess.

  • A deleted person is unlinked from projects, milestones, and meeting attendee and core-staff records, and is cleared as PI from any project that listed them.
  • The attendee names shown on a booking are recomputed, so a deleted person stops appearing there — that display list is stored separately from the actual attendee links and used to drift out of sync.
  • A deleted instrument is unlinked from projects, milestones, and bookings; affected bookings lose the line item but keep their saved totals.

A palette of its own 1.3.7

The app had been wearing the stock Tailwind indigo/violet it inherited from the template it started life on — the same colours as a great many other apps. 1.3.7 recoloured it end to end onto a distinct neutral/violet system: backgrounds, borders, text, and the success/warning/danger states, in both light and dark themes, with every pairing checked to WCAG AA contrast. Dark-mode primary buttons picked up a dedicated dark-ink label colour, fixing a contrast failure against the lighter dark-mode primary.

  • The logo gradient and the PWA theme colours (favicon, manifest, theme-color meta) moved to the same identity.
  • Shared motion tokens replaced hand-tuned transition timings, with a prefers-reduced-motion override for anyone who asks their system for less animation.
  • No layout, typography, or component-structure changes — same app, new colours. Every screenshot on this page and in the README was re-captured for it.

A bug the screenshots found 1.3.9

Capturing the “Delete Field” dialog above turned out to be impossible by clicking, because the icon that opens it could not be clicked at all. A custom field’s Edit and Delete icons are bare spans, so none of the CSS rules that size the app’s inline icons applied to them — measured in a browser, both were 0 pixels wide, and a click where they should be landed on the row behind. Once a custom field was saved, it could never be edited or removed. Both now have a proper 22×22 hit area, which is also what makes 1.3.8’s new confirmation reachable in the first place.

Under the hood: cascades, verified

The codebase carried two contradictory comments about whether the database’s ON DELETE CASCADE rules actually fire, after an old note claimed the SQLite build silently disables foreign keys when it saves. That got settled empirically for 1.3.8 by running the app’s own bundled SQLite build headlessly: saving does reset the foreign-key setting, and the app’s existing re-assert after every save does restore it, so cascades work. The delete paths clean up their child records explicitly anyway — belt and suspenders, in case some future save path ever forgets that re-assert.
